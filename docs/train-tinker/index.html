Train with Tinker

Use the MATH harness to collect continuations and update the policy through Tinker. FOCUS selects which continuations to collect and computes an advantage for each segment. Tinker then trains on those segments, using their original tokens and generation probabilities. Each actor update overlaps with collection of the next batch, keeping the sampling policy at most one optimizer step behind the learner.

With Tinker, your script owns the training loop. focus.integrations.tinker supplies its pieces: data conversion, one actor update, and the one-step asynchronous loop. You supply the task: a function that builds the collector for one problem. Train with Slime asks for the same function, so the task code below serves both trainers.

Before you begin

Section titled “Before you begin”

Use the environment and context manager from Quick start: MATH. Install python -m pip install -e '.[tinker]' in the FOCUS checkout, install tinker==0.35.0 for this example, and set TINKER_API_KEY for your account.

We will put the task in math_training.py and the launch in train_tinker.py.

1. Describe the task: one collector per problem

Section titled “1. Describe the task: one collector per problem”

Each training item is a Problem: the prompt the policy sees, and a label that stays out of the prompt — here the reference solution the environment grades against. A trainer integration knows which weights are sampling. For every problem, it asks for the collector to run under that policy.

Create math_training.py with the imports and the search configuration:

math_training.py
from focus import Collector, Critic, Selective

from math_quickstart import make_agent


def search_config():
    """A FIFO warm-up, then selective allocation by expected critic-error reduction."""
    return Selective(budget=32, warmup=16, max_concurrency=1)

Selective starts with a first-in, first-out phase with a budget of 16 task transitions and at most two branches per state. The next phase has a budget of 32 transitions and prioritizes expected critic-error reduction. Here max_concurrency=1 runs one continuation at a time across the tree. A transition is one generated MATH segment; each phase lets its running continuation finish, so actual usage can exceed the launch budget.

Connect the search to the task with a starting critic, then answer the integration’s question:

math_training.py
def math_context(policy):
    """Give the critic the exact MATH prefix, including unfinished reasoning."""
    def render(rollout):
        if rollout.turns:
            last = rollout.turns[-1]
            tokens = last.prefix + last.tokens
        else:
            tokens = policy.prepare(rollout.messages).tokens
        return policy.decode(tokens)
    return render


def make_collector(policy, solution, *, critic=None, search=None, execution=None):
    if critic is None:
        # A uniform starting prediction for the first collection round.
        critic = Critic.constant(0.5, context=math_context(policy))
    return Collector(
        make_agent(policy, solution, policy.decode, execution=execution),
        critic=critic,
        search=search if search is not None else search_config(),
    )


def collector_for(policy, problem):
    """What both trainers ask for: the collector for one MATH problem under a policy.

    ``problem.prompt`` is the question the policy sees; ``problem.label`` is the
    reference solution, which stays inside the environment for grading.
    """
    return make_collector(policy, problem.label)

Critic.constant(0.5) predicts 0.5 for every unfinished state, giving the first round the same starting estimate at each checkpoint. math_context() decodes the recorded prompt and generated tokens at each checkpoint. At the root, it renders the initial chat prompt. It preserves a partial solution’s thinking and whitespace without inserting another chat turn. The same text is sent to the critic and saved in its training records.

collector_for(policy, problem) is the whole task-specific supply. It binds the problem’s reference solution into a fresh environment, so concurrent problems never share an answer. The integration calls it with the policy for the current sampler and uses each collector once.

2. What the integration collects

Section titled “2. What the integration collects”

For each problem, the integration wraps the current Tinker sampling client in a TinkerPolicy. The sampling client is a frozen snapshot of the learner’s weights, so the learner can update while a FOCUS tree keeps using its original sampler. It then calls collector_for and collects one tree. profile="token_chunk" resolves the sampler’s tokenizer for a model used without tools; Segments in the shared make_agent() reads each reply as an exact 256-token segment.

Preparation computes the tree values once. For each expanded state with a critic prediction, the mean direct-branch backup Gˉ\bar GGˉ becomes a critic target. Combining that mean with the critic’s prediction gives the refined value V~\tilde VV~ that DirectBranchTd uses to compute segment advantages. A collection with failed expansions or critic predictions raises unless you pass allow_partial=True.

The export labels each record by its training role, or lane:

LaneLearning signalTraining input
ActorSegment advantage, stored in rewardExact tokens, loss mask, and behavior log probabilities
CriticBackup target, stored in targetThe checkpoint’s serialized context

Each generation records the log probabilities of its sampling snapshot, and they stay with the exported tokens after the learner moves to newer weights. Both lanes’ records carry metadata["training"]: the batch index, the problem’s id, and behavior_step, the number of completed optimizer updates when the sampler was taken. Critic records also carry the learner_step that trained on their batch.

To change the phases, priorities, or budgets, build a different collector in collector_for. To select another recipe or inspect a tree, use the collection APIs.

3. Turn actor segments into next-token targets

Section titled “3. Turn actor segments into next-token targets”

A language model predicts the next token. For an exported sequence [prompt, segment], Tinker’s input is tokens[:-1] and its target is tokens[1:]; the behavior log probabilities and mask shift by the same position. focus.integrations.tinker.to_datum(record) performs this conversion and returns a Tinker Datum.

Suppose a segment has advantage 0.30.30.3. Every generated token in that segment receives advantage 0.30.30.3; every prompt token receives zero. A segment with advantage −0.2-0.2−0.2 receives negative weights on its generated tokens. This teaches the actor which steps improved the expected outcome while leaving conditioning text masked. See Tinker’s data format.

The exported reward is the actor weight, used directly. The recorded log probabilities supply the behavior-policy term in the learner-to-behavior probability ratio.

4. Compute gradients and apply the update

Section titled “4. Compute gradients and apply the update”

update_actor(training_client, records, learning_rate=...) converts the actor lane, calls forward_backward_async() for the clipped policy-gradient loss, and then optim_step_async() for the optimizer update. It awaits the backward result before submitting the optimizer step, and the optimizer result before returning, so a sampler published afterwards holds the updated weights. Collection on an existing sampler continues during both operations.

The default loss is Tinker’s ppo with clipping thresholds 1±0.21 \pm 0.21±0.2, matching the paper’s token-level PPO objective; pass loss_fn and loss_fn_config to change it. See Tinker’s PPO loss.

5. Export the critic targets for the next round

Section titled “5. Export the critic targets for the next round”

Neither trainer trains the critic. The integration hands each batch’s critic records to a critic sink; JsonlDirectory(path) writes one JSONL file per batch, with one context and target for each expanded nonterminal state. Fit your value model to these targets with mean squared error:

Lcritic=1N∑j=1N(Vϕ(cˉj)−Gˉ(cˉj))2.\mathcal L_{\mathrm{critic}} = \frac{1}{N}\sum_{j=1}^{N} \left(V_\phi(\bar c_j)-\bar G(\bar c_j)\right)^2.Lcritic​=N1​j=1∑N​(Vϕ​(cˉj​)−Gˉ(cˉj​))2.

For example, a record with target 0.6 asks the critic to predict remaining return 0.6 from that partial solution. The actor’s signed advantage has a different purpose and stays in the actor lane.

Train the scalar critic in your value-model loop, then expose it through a Critic. Use the same context rendering for training and collection. Keep the actor and critic snapshots fixed for each tree, and publish updated models for newly launched collections; a tree already in flight keeps its original snapshots. This example keeps Critic.constant(0.5) until you supply a trained critic.

Connect a trained scalar critic

Section titled “Connect a trained scalar critic”

For a value model served through vLLM pooling, give every collector the same critic:

from focus.backends import VLLMCritic

critic = None  # one critic for the whole run

def collector_for(policy, problem):
    global critic
    if critic is None:  # rendering only decodes, so any snapshot's policy will do
        critic = VLLMCritic(
            base_url=critic_url,
            model=critic_model,
            reduce="last",
            context=math_context(policy),
        )
    return make_collector(policy, problem.label, critic=critic)

critic_url is the vLLM server root, which serves the pooling endpoint, and critic_model is its served model name. reduce="last" selects the last pooled score. Train this score to predict remaining task return: on our binary-outcome task, 0.7 means an estimated 70% chance of eventual success. context=math_context(policy) uses the same partial-solution text that was exported for critic training. A collector does not close its critic: close it with await critic.aclose() after train() returns.

6. Overlap collection and training with one-step lookahead

Section titled “6. Overlap collection and training with one-step lookahead”

First collect batch 0 with the initial policy πθ0\pi_{\theta_0}πθ0​​. Then collect batch 1 from that same snapshot while the learner updates on batch 0. After the update, publish πθ1\pi_{\theta_1}πθ1​​ for the next collection. Batch 1 still carries the probabilities from πθ0\pi_{\theta_0}πθ0​​.

For a three-update run, the schedule is:

PhaseLearnerCollection
Warm-upWait for the first batchBatch 0 with πθ0\pi_{\theta_0}πθ0​​
Update 0Train on batch 0: θ0→θ1\theta_0 \to \theta_1θ0​→θ1​Batch 1 with πθ0\pi_{\theta_0}πθ0​​
Update 1Train on batch 1: θ1→θ2\theta_1 \to \theta_2θ1​→θ2​Batch 2 with πθ1\pi_{\theta_1}πθ1​​
Update 2Train on batch 2: θ2→θ3\theta_2 \to \theta_3θ2​→θ3​All requested batches collected

focus.integrations.tinker.train(...) runs this schedule. It holds at most one upcoming collection: if collection finishes first, its batch waits for the learner; if training finishes first, the learner waits for that batch. Before every update it checks the batch index and computes lag = step - batch.behavior_step; with async_depth=1, the accepted lag is zero or one. Every batch trains exactly once, including the last one, and no unused collection launches after it. The loop publishes a new sampler only after an optimizer step completes and only when another collection remains, running the SDK’s blocking snapshot call in a worker thread.

Set async_depth=0 to collect each batch after the preceding update, with the current learner weights. The one-step schedule overlaps those operations while keeping one actor snapshot and one critic snapshot fixed within each tree. When adding critic updates, pass a fixed critic snapshot to each collection as well.

If the loop stops early, it cancels and awaits any outstanding local collection. An update that has already reached Tinker can still complete remotely; a failed run stops rather than retrying that update.

7. Assemble the entry point and save training state

Section titled “7. Assemble the entry point and save training state”

Read the MATH records, create the LoRA training client, and run the loop:

train_tinker.py
def read_problems(path):
    """Read MATH records from one JSON object, a JSON array, or JSONL."""
    path = Path(path)
    text = path.read_text()
    rows = ([json.loads(line) for line in text.splitlines() if line.strip()]
            if path.suffix == ".jsonl" else json.loads(text))
    if isinstance(rows, dict):
        rows = [rows]
    if not isinstance(rows, list) or not rows or any(
        not isinstance(row, dict) or
        not all(isinstance(row.get(key), str) and row[key].strip() for key in ("problem", "solution"))
        for row in rows
    ):
        raise ValueError("Provide MATH records with nonempty problem and solution strings")
    return [Problem(row["problem"], row["solution"], row.get("id", i)) for i, row in enumerate(rows)]


async def main(args):
    import tinker
    problems = read_problems(args.problem_file)
    if args.steps < 1:
        raise ValueError("--steps must be positive")
    service = tinker.ServiceClient()
    status = "errored"
    try:
        training = await service.create_lora_training_client_async(base_model=args.model, rank=32)
        await train(
            training, model=args.model, problems=problems, collector_for=collector_for,
            steps=args.steps, async_depth=args.async_depth, learning_rate=args.learning_rate,
            # The model is used without tools; Segments reads each reply as a token chunk.
            profile="token_chunk",
            critic_sink=JsonlDirectory(args.critic_output),
            on_step=lambda report: print(json.dumps(asdict(report))),
        )
        checkpoint = await training.save_state_async(name=f"after-{args.steps}-updates")
        saved = await checkpoint.result_async()
        print(f"Training checkpoint: {saved.path}")
        print(f"Critic targets: {args.critic_output}")
        status = "success"
    except (asyncio.CancelledError, KeyboardInterrupt):
        status = "interrupted"
        raise
    finally:
        await service.close(status=status)

read_problems() accepts one JSON record, a JSON array, or JSONL. Each record supplies problem and solution, plus an optional id, and becomes a Problem. Each training batch collects one problem; the loop cycles through them until it reaches steps updates. on_step receives a report per update: batch index, behavior step, learner step, policy lag, and Tinker’s metrics.

save_state_async() saves the learner’s model and optimizer after the final batch has trained. Await its returned future to get the checkpoint path. The service closes after success, failure, or interruption. See Tinker’s checkpoint API and session lifecycle.

To start another run from that checkpoint, use service.create_training_client_from_state_with_optimizer_async(checkpoint_path) in place of creating a fresh LoRA client. The new run starts with an empty pipeline and a sampler from the restored learner; step labels start at zero. Write its critic records to a new directory so the two runs’ targets stay apart.

A learner checkpoint stores model and optimizer state. A FOCUS rollout checkpoint stores an agent’s state for branching, as shown in BrowseComp-Plus.

8. Run three overlapping collection and update steps

Section titled “8. Run three overlapping collection and update steps”

Install FOCUS with its Tinker client and the math verifier:

python -m pip install -e '.[tinker]'
python -m pip install 'tinker==0.35.0' 'math-verify[antlr4_13_2]==0.9.0'

Save these files in the same directory:

  • math_quickstart.py: the task environment and 256-token harness.
  • math_training.py: the search and the collector for one problem.
  • train_tinker.py: problem loading and the launch.

Set TINKER_API_KEY for your account and FOCUS_MODEL to a model available to your Tinker service with a compatible chat tokenizer. Supply a MATH record as shown in the quick start, or a dataset of records:

python train_tinker.py \
  --model "$FOCUS_MODEL" \
  --problem-file problems.jsonl \
  --steps 3 \
  --async-depth 1 \
  --learning-rate 1e-5

This command takes three actor updates, saves the final training checkpoint, and writes critic targets from all three batches to the critic-targets directory. Each printed line reports one update; the expected lags are 0, 1, 1. Use --async-depth 0 for synchronous collection or --steps 1 for a single-update smoke run.

Tinker launch
train_tinker.py
"""Train a Tinker actor with one-step asynchronous FOCUS MATH collection."""
import argparse
import asyncio
from dataclasses import asdict
import json
from pathlib import Path

from focus.integrations import JsonlDirectory, Problem
from focus.integrations.tinker import train
from math_training import collector_for


def read_problems(path):
    """Read MATH records from one JSON object, a JSON array, or JSONL."""
    path = Path(path)
    text = path.read_text()
    rows = ([json.loads(line) for line in text.splitlines() if line.strip()]
            if path.suffix == ".jsonl" else json.loads(text))
    if isinstance(rows, dict):
        rows = [rows]
    if not isinstance(rows, list) or not rows or any(
        not isinstance(row, dict) or
        not all(isinstance(row.get(key), str) and row[key].strip() for key in ("problem", "solution"))
        for row in rows
    ):
        raise ValueError("Provide MATH records with nonempty problem and solution strings")
    return [Problem(row["problem"], row["solution"], row.get("id", i)) for i, row in enumerate(rows)]


async def main(args):
    import tinker
    problems = read_problems(args.problem_file)
    if args.steps < 1:
        raise ValueError("--steps must be positive")
    service = tinker.ServiceClient()
    status = "errored"
    try:
        training = await service.create_lora_training_client_async(base_model=args.model, rank=32)
        await train(
            training, model=args.model, problems=problems, collector_for=collector_for,
            steps=args.steps, async_depth=args.async_depth, learning_rate=args.learning_rate,
            # The model is used without tools; Segments reads each reply as a token chunk.
            profile="token_chunk",
            critic_sink=JsonlDirectory(args.critic_output),
            on_step=lambda report: print(json.dumps(asdict(report))),
        )
        checkpoint = await training.save_state_async(name=f"after-{args.steps}-updates")
        saved = await checkpoint.result_async()
        print(f"Training checkpoint: {saved.path}")
        print(f"Critic targets: {args.critic_output}")
        status = "success"
    except (asyncio.CancelledError, KeyboardInterrupt):
        status = "interrupted"
        raise
    finally:
        await service.close(status=status)


if __name__ == "__main__":
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--model", required=True)
    parser.add_argument("--problem-file", required=True, help="MATH JSON object, JSON array, or JSONL")
    parser.add_argument("--steps", type=int, default=3, help="Actor updates; cycle through the input records")
    parser.add_argument("--async-depth", type=int, choices=(0, 1), default=1,
                        help="1 overlaps next collection with training; 0 collects synchronously")
    parser.add_argument("--critic-output", default="critic-targets",
                        help="Directory for the critic records, one JSONL file per batch")
    parser.add_argument("--learning-rate", type=float, default=1e-5)
    asyncio.run(main(parser.parse_args()))

Collection and execution with Tinker

Section titled “Collection and execution with Tinker”

Run train_tinker.py as one Python process. It owns the environments, rollout trees, and training loop. Tinker serves generation and optimizer requests remotely, so this tutorial needs no Ray cluster or separate collection service.

The run has two independent concurrency controls. --async-depth 1 overlaps one upcoming batch with the current update. Selective(max_concurrency=...) controls simultaneous branch continuations within that batch. To allow four continuations at once, return collectors with a wider search:

from focus import Selective

def collector_for(policy, problem):
    search = Selective(budget=32, warmup=16, max_concurrency=4)
    return make_collector(policy, problem.label, search=search)

This keeps the same rollout budget and one-batch lookahead. All branches in a tree use the same sampling client and fixed critic; increasing concurrency does not introduce another model snapshot. Throughput depends on the capacity available to your Tinker account.

Each collector closes its local execution services when its collection finishes. Your script owns the Tinker session: the loop cancels and awaits any pending collection before main() closes that session. For a trainer that manages its own inference workers, see Train with Slime.
